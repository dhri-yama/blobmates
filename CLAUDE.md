# CLAUDE.md

Guidance for working in this repo. For what the project is, see `README.md`. For visual rules, see `DESIGN.md`.

## What this is

Polypals: deterministic blob avatars. `avatar(seed, options)` returns an SVG string; `animate(host, avatar, options)` makes one alive in the browser. A React site in `web/` (landing, editor, docs) shows it off.

## Commands

```bash
node core/tools/build-parts.mjs     # regenerate core/assets/parts.json (run after ANY art or mood change)
cd web && npm install
cd web && npm run dev          # dev server
cd web && npm run build        # static site in web/dist
(cd core/js && npm test)         # unit tests for the library
node core/tools/serve.mjs      # serves the repo root on :5173 (PORT=... to change); the built site is at /web/dist/index.html
```

There are no automated tests yet. Verify changes by rebuilding and looking at the page.

## Layout

- The repo has two parts: `core/` (shared data, tools and the library) and `web/` (the React site). New language ports go in `core/` next to `js/`.
- `core/assets/parts.json` is GENERATED. Never edit it by hand. All art and mood data lives in `core/tools/build-parts.mjs`.
- `core/js/src/index.js` is the core (seed to SVG). It must stay free of DOM and browser APIs so it can run on a server and be ported.
- `core/js/src/runtime.js` is browser-only (motion, blink, gaze, roam, tap reaction).
- `core/js` is also the npm package `polypals` (`package.json`, `LICENSE`, `README.md`, `types/`). Entries: `polypals` (`main.js`), `polypals/runtime`, `polypals/react` (`react.js`, written with `createElement`, no build step). `src/parts.js` is generated by the same script as `parts.json`.
- `web/src/` is the React app. It imports the library and `parts.json` from `core/` with relative paths, so build it from this repo, not from a copy of `web/`.

## Rules that are easy to break

- **Seed draw order is a contract.** In `resolve()` (`index.js`) every random draw happens in a fixed order, even for unused values. Add new draws at the END, never in the middle, or every existing avatar changes. Adding or removing bodies, mouths or accessories also changes what some seeds pick, so treat a released parts set as a version.
- **Integer math only in seed logic** (`Math.imul`, `>>>`, `%` on integers). No floats or locale-dependent formatting in anything that decides a choice, because Kotlin and Swift ports must match exactly.
- **Placeholders in art fragments:** `{{body}}` (fur color), `{{acc}}` (accessory color), `{{shade}}` (darker body color), `{{lid}}` (eyelid color). They are replaced once at the end of `avatar()`.
- **Coordinate system:** everything is drawn on a 100x100 viewBox. The face has its own frame: eyes at y=46, x=36 and x=64, mouth around y=66 to 75. Bodies position the face with `fx`, `fy`, `fs`. Bodies can have a `back` layer (behind the body) and `front` layer (over the body, under the face). The whole avatar is scaled to 0.88 inside the viewBox so shapes fit a circular crop.
- **Anatomy hooks:** parts carry `data-part="..."` (`eyes`, `pupil-l`, `pupil-r`, `mouth`, `overlay`, ...). The runtime relies on them. Do not remove or rename them.
- **Motion is data.** Per-mood motion numbers (bounce, tilt, tremble, roam speed, blink interval) live under `moods.<name>.motion` in `parts.json`. Change the numbers in `build-parts.mjs`, not the runtime. Mood overlays (thought bubble, snoring) are frame lists in `overlays`.
- **The runtime re-renders the SVG string** when gaze, blink or an overlay frame changes. Keep per-frame work cheap, and quantize anything that would otherwise change every frame.

## Web app notes

- Routing is a tiny hash router (`router.js`), so any static host works. Add pages in `web/src/pages/` and register them in `App.jsx`.
- Code samples in the editor and docs come from `web/src/snippets.js`. Update it when the public API changes, and update the Docs page (`pages/Docs.jsx`) in the same change. Only the JavaScript, React and HTML samples are known to run; Vue, Svelte and Angular are untested.
- The package is not published, so every sample imports local paths like `./polypals/index.js`.
- Editor controls use "pins": an unpinned axis follows the seed. Keep that behavior when adding controls (a pin is an option key, `undefined` means auto).

## Gotchas learned the hard way

- After editing `styles.css` with scripted find-and-replace, check that braces are balanced. A stray `@media(...){` once swallowed every rule after it and left the site unstyled on wide screens only.
- The preview pane here is narrow (around 540 CSS px). Layouts that switch at 560px, 760px or 1100px need an emulated viewport to check.
- Rebuild `web/dist` (`npm run build`) after changing the app, or the preview server shows the old version.

## Conventions

- Plain ES modules, no TypeScript, no build step for the library.
- Match the surrounding style: short comments that explain why, not what.
- Do not publish, push or deploy without being asked. The GitHub repo is public.

## Versioning

Two numbers, kept separate:

- **Package version** (`core/js/package.json`): semver, shown on npm.
- **Parts version** (`version` in `core/tools/build-parts.mjs`, stored in `parts.json`): bump it whenever a change alters what existing names pick, meaning the seed logic, the draw order, or the lists of shapes, mouths, brows, accessories or palettes. Pure additions to those lists count, because the seed indexes into them.

Rules for the package version:

| Change | Bump |
|---|---|
| Bug fix, docs, motion tuning, new art that does not change picks | patch |
| New option, mood, overlay or entry point; anything that keeps existing avatars the same | minor |
| Changes what an existing name picks, removes or renames an option or export | major |

While the version is 0.x, a change to what names pick may ship in a minor bump, but it must be listed in the changelog. From 1.0.0, it is a major bump. Tell users to pin `body` (and other options) if an avatar must never change across upgrades.

Every release gets an entry in `core/js/CHANGELOG.md` and a git tag `vX.Y.Z` on the release commit.

## Releasing to npm

1. Update `core/js/CHANGELOG.md`, then bump the version: `cd core/js && npm version <patch|minor|major> --no-git-tag-version`. If the parts changed in a way that changes picks, also bump the parts version first (see above) and regenerate.
2. `node core/tools/build-parts.mjs && (cd core/js && npm test)`.
3. `cd core/js && npm pack` and install the tarball in a scratch project to check the real package (imports, React server rendering, types).
4. Commit and push, then publish: `cd core/js && npm publish` (needs `npm login` and 2FA; the `public` access is set in `package.json`). `prepublishOnly` reruns the generator and the tests.
5. Tag and push the tag: `git tag vX.Y.Z && git push origin vX.Y.Z`. Optionally create a GitHub release from the tag with the changelog text.
6. After the first publish only: switch the Docs page, `snippets.js` and the README from local `./polypals/...` imports to `polypals`.

## Known gaps

Unit tests exist for the JS library only. There are no stored seed outputs for ports to check against, no Kotlin or Swift ports, and the web app does not yet use the packaged React components (it has its own). The `togepi` shape is inspired by a Nintendo/Pokémon character, so flag it if the project is ever distributed commercially.
